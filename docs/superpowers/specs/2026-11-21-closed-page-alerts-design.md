# Closed-page flood alerts (Web Push) — design

Date: 2026-11-21 · Status: for owner approval

## Intent

Residents of Cinangka Paradisa Residence get a phone notification when the
Pesanggrahan river is at WASPADA or higher **even when the page is closed**.
Today the only warning is the in-page chime + `Notification`, which fires only
while the tab is open (`useTransitionAlert`). The owner keeps the page on an
iPhone and wants to be warned without it open.

First target: iPhone (iOS 16.4+, page added to Home Screen). Android Chrome
works through the same Web Push standard and is not special-cased.

## Decisions made with the owner

| Topic | Decision |
|---|---|
| Who can subscribe | Anyone who opens the page — residents, not just the owner. |
| Trigger | Level at **WASPADA (≥ 150 cm) or higher**, **at most once per hour** while it stays there. |
| All-clear | One "back to normal" push only after **two consecutive new readings below 150 cm** (≈ 1 h with BPBD's hourly table, ≈ 20 min with the sensor). |
| Where it runs | **The owner's existing Vultr VPS** (approach B). Cloudflare Workers was dropped: the free plan's 10 ms CPU per cron run covers only ~5–8 encrypted pushes, and Workers Paid ($5/mo) was declined. |
| Notification content (approved sketch) | `WASPADA · 200 cm ▲ naik` / `Pos Pesanggrahan, 19:00 · +10 cm/jam · SIAGA at 250 cm` |

## Calls made by Claude, accepted by the owner

- **Band escalation pushes immediately** (WASPADA → SIAGA → BAHAYA), even if
  the previous push was under an hour ago.
- **No quiet hours** — floods come at night.
- **Same data rule as the page:** sensor first, BPBD hourly manual reading only
  when strictly newer (`pickReading`). A reading **older than 2 h never
  triggers a push**.
- **No accounts, no personal data:** store only the anonymous push
  subscription, its locale and timestamps.
- **Notification language** = the page's EN/ID setting at subscribe time.
- **Turning alerts off** is one tap on the same control.

## Goals

1. A subscribed iPhone home-screen app receives a notification within ~5–10 min
   of a qualifying reading becoming available upstream (BPBD posts hourly
   readings with up to ~1 h lag; that lag is upstream and accepted).
2. Pushes follow the trigger rules exactly.
3. A resident can turn alerts on and off from the page in under a minute,
   including the iPhone Add-to-Home-Screen step, guided in EN/ID.
4. No new monthly cost; runs beside mykid, RustDesk and wg-easy without
   disturbing them.

## Non-goals

- Accounts, logins, per-user thresholds, quiet-hour settings.
- SMS / WhatsApp / Telegram delivery.
- Rain-forecast alerts — water level only.
- Android-specific UI polish.
- Replacing the in-page chime; it stays for the open page.

## Anti-goals (failure even if it "works")

- **Silent death:** the watcher stops (upstream blocked, crash, VPS down,
  expired keys) and nobody notices while residents believe they are covered.
- **Crying wolf:** stale or cached data announced as new, flip-flopping around
  a threshold or between sources, duplicate pushes — residents learn to ignore
  it. (The page just had this bug class: a cached 18-Nov reading re-triggered
  "rising" alerts.)
- **Storing anything that identifies a resident.**
- **An open relay:** the server POSTing to arbitrary URLs supplied by clients.
- **Disturbing the VPS's other services** (mykid, RustDesk `hbbs`/`hbbr`,
  `wg-easy`), including restarting mykid's tunnel.

## Constraints and facts

- **iOS Web Push:** only for a web app opened from the Home Screen
  (`display: standalone` — already in the manifest), iOS 16.4+. Permission must
  be requested from a user tap inside the installed app. Every push **must**
  show a notification (`userVisibleOnly: true`) or iOS may revoke the
  subscription. A Safari bookmark/tab cannot receive pushes.
- **Icons:** manifest and `apple-touch-icon` use only `favicon.svg`; iOS
  ignores SVG touch icons. Needs PNGs (180×180 touch icon; 192 and 512
  manifest icons).
- **Service worker** is generated by `vite-plugin-pwa` (`generateSW`,
  `registerType: 'autoUpdate'`). A `push` and `notificationclick` handler must
  be added (`workbox.importScripts` or switch to `injectManifest`).
- **Upstream reachability from the VPS — verified 2026-11-21:** BPBD
  `api/charttma` 200 × 3 (~0.4 s, real table); DSDA `GenerateDataTinggiAir`
  200 (131 B — gate 160 still silent).
- **VPS:** Vultr, `root@45.77.33.192`, 1 vCPU, 955 MB RAM (~477 MB available),
  Docker. Running: `mykid-app-1`, `mykid-cloudflared-1`, `wg-easy`, `hbbs`,
  `hbbr`. mykid's pattern (`~/projects/mykid/deploy/`): its own Compose
  project, its own `cloudflared` tunnel container (`TUNNEL_TOKEN` in
  `deploy/.env`, mode 600, never in git), no published host ports,
  `read_only`, `mem_limit`, healthcheck, and a `deploy.sh` that refuses to
  deploy unless the neighbours are up and re-checks them afterwards. Tunnel +
  DNS set up by `deploy/cloudflare/setup_tunnel.py` with a Cloudflare API
  token read from `~/.config/mykid/cf_token`.
- **Shared logic:** `app/src/lib/{bpbd,manualFallback,siaga,analytics,upstream}.ts`
  are pure TS. The server reads the DSDA **time-series** (plain text →
  `parseHistoryBody`) and BPBD (`parseBpbdReadings`), then
  `sensorReading(null, history, defaults)` → `pickReading(...)`. It does
  **not** use `parseSnapshotXml` (needs `DOMParser`) or `fetchText` (browser
  `cache` option); it does its own `fetch` and calls the parsers.
- **BPBD table** is today-only and resets at midnight; the server persists and
  merges it (`mergeManualTables`) like the page does in `localStorage`.
- **Bands use ≥:** exactly 150 / 250 / 350 cm is WASPADA / SIAGA / BAHAYA,
  matching the owner's words and the page legend ("150 - 250 cm").
  `classify()` in `app/src/lib/siaga.ts` currently uses `>`; change it so page
  and server agree (BPBD reports in 5 cm steps, so exact values are common).
  *(Claude's call.)*
- **Deploys:** the page is still deployed by the owner with `wrangler pages
  deploy` (Claude's shell can't authenticate wrangler). The VPS service is
  deployed over SSH (`root@` key login works from Claude's shell), like mykid.
- Repo conventions: TS + Vitest, TDD, immutable data, small files, EN/ID
  strings in `app/src/i18n/messages.ts`, 80%+ coverage on library code.

## Approaches considered

- **A. Cloudflare Worker + Cron Trigger.** Free and serverless, but the free
  plan allows 10 ms CPU and 50 outbound requests per cron run
  (developers.cloudflare.com/workers/platform/limits), enough for only ~5–8
  encrypted pushes per run; scaling to a residence needs Workers Paid
  ($5/mo, declined) or a fragile fan-out across runs.
- **B. Small service on the existing Vultr VPS (chosen).** No CPU cap, no new
  cost, mature Web Push libraries, upstream verified reachable from it.
  Costs: one more container on a small box (capped at 128 MB), and the owner's
  VPS becomes the single point of failure (see Monitoring).
- Rejected earlier: the owner's Mac (sleeps / loses its tunnel → silent death);
  third-party apps (residents must install something instead of tapping a
  button on the page).

## Design

### Components

1. **`alerts/` — Node 22 + TypeScript service** (new, in this repo).
   *(Claude's call: Node/TS rather than Python like mykid, so the river logic —
   BPBD date stamping, midnight merge, sensor-vs-manual choice, bands — has one
   tested implementation shared with the page instead of a port that can
   drift. `web-push` (npm) is the reference Web Push library.)*
   - Bundled with esbuild into one file, importing `../app/src/lib/*`.
   - **Watcher loop** (in-process, every 5 min): fetch DSDA time-series (24 h)
     and BPBD (one retry on failure); merge BPBD into the persisted table;
     compute the current reading with the shared logic; run the alert rules;
     send pushes; persist state.
   - **HTTP API** on `https://banjir-api.achmadnaufal.com` via its **own**
     Cloudflare Tunnel. CORS allows only `https://banjir.achmadnaufal.com`
     (plus localhost for dev). *(Claude's call: direct CORS is one less moving
     part than proxying through a Pages Function; a one-level subdomain keeps
     Cloudflare's free certificate.)*
     - `GET  /api/push/key` → VAPID public key.
     - `POST /api/push/subscribe` `{subscription, locale}` → upsert.
     - `POST /api/push/unsubscribe` `{endpoint}` → delete.
     - `POST /api/push/test` `{endpoint}` → one test notification to that
       subscription only.
     - `GET  /api/push/status` → watcher health (see Monitoring).
     - `GET  /healthz` → container healthcheck.
   - **Storage: SQLite** in a Docker volume. Tables: `subscriptions`
     (endpoint PK, p256dh, auth, locale, is_owner, created_at, last_ok_at),
     `state` (single row: last_band_announced, last_push_at,
     last_pushed_reading_at, below_count, bpbd_table JSON, last_run_at,
     last_run_ok, last_error, failing_since).
   - Web Push with VAPID; keys generated once, stored only in
     `alerts/deploy/.env` on the VPS (mode 600) and never in git.
   - Subscriptions answering **404/410** are deleted; other failures are
     logged and retried next run.

2. **VPS deployment** — mirrors mykid:
   `alerts/deploy/compose.yaml`, Compose project `banjir-alerts`: `app`
   (`mem_limit: 128m`, `read_only`, tmpfs `/tmp`, volume for SQLite,
   healthcheck on `/healthz`, `restart: unless-stopped`) + its own
   `cloudflared` (own tunnel, own `TUNNEL_TOKEN`). No published host ports.
   `alerts/deploy/deploy.sh` refuses to deploy unless `hbbs`, `hbbr`,
   `wg-easy`, `mykid-app-1` and `mykid-cloudflared-1` are up, runs tests,
   rsyncs to `/opt/banjir-alerts`, builds, waits for healthy, re-checks the
   neighbours, then checks `https://banjir-api.achmadnaufal.com/healthz`.
   Tunnel + DNS via a setup script modelled on mykid's `setup_tunnel.py`.

3. **Page (`app/`)**
   - An "alerts while closed" control replacing/extending `AlertOptIn`:
     - iOS Safari **not** standalone → Add-to-Home-Screen steps (EN/ID)
       instead of a button.
     - Standalone (or a push-capable browser) → **Turn on alerts** →
       permission → `pushManager.subscribe` → `POST /api/push/subscribe`.
     - On → "Alerts are on for this phone" + **Send test** + **Turn off**.
     - Permission denied → how to re-enable in iOS Settings.
     - A small line: "Alert service checked N min ago", from `/status`; a
       warning if the last good run is > 20 min old.
   - Service-worker `push` handler shows the notification from the payload;
     `notificationclick` focuses/opens the app. Same `tag` scheme as the
     in-page alert (`banjir-<band>`) so an open page and a push don't stack.
   - PNG icons added to the manifest and `apple-touch-icon`.
   - `classify()` changed to `≥` (see Constraints), tests updated.

### Alert rules (server, pure function, fully unit-tested)

Input: current reading `{levelCm, band, observedAt, source, prevLevelCm,
ratePerHour?}`, persisted `state`, `now`.
Output: `{push: none | alert | escalation | allClear, nextState}`.

- `last_band_announced` is the last band **pushed**, not the last observed —
  a 249 ↔ 251 cm wobble escalates once; a drop from SIAGA to WASPADA is
  announced at the next hourly update (≤ 1 h). *(Claude's call.)*
- Reading missing, or `now − observedAt > 2 h` → **no push**, state unchanged
  (recorded for Monitoring).
- Only a **new** reading (`observedAt > last_pushed_reading_at`) can push.
- band ≥ WASPADA and `last_band_announced` is NORMAL/none → **alert**;
  reset `below_count`.
- band higher than `last_band_announced` → **escalation**, immediately.
- band ≥ WASPADA, not higher than announced, and the reading is ≥ 60 min
  newer than the last pushed one (`observedAt − last_pushed_reading_at`)
  → **alert** (hourly update; the payload shows direction, so a falling
  level reads as falling); reset `below_count`. Measured on reading times,
  not push times: BPBD's posting lag varies, so wall-clock spacing would
  skip every other hourly reading. *(Refined while planning.)*
- band NORMAL while `last_band_announced` ≥ WASPADA → `below_count += 1`
  per new reading; at **2** → **allClear** once and
  `last_band_announced = NORMAL`. A reading back at ≥ WASPADA before that
  resets `below_count` and does not re-alert (no all-clear was sent), so it
  falls under the hourly rule.
- A band change caused only by the sensor ↔ BPBD switch gets no special
  handling: `pickReading` switches only when the sensor goes quiet or comes
  back, and the all-clear hysteresis absorbs a flip. *(Claude's call.)*
- First run with no state: `last_band_announced` = NORMAL (a resident
  subscribing mid-flood gets the status on the next new reading).
- A new subscriber does not get an immediate push for the ongoing state
  beyond the test push they can send themselves. *(Claude's call.)*

Payload (per subscriber locale): title `"<BAND> · <cm> cm <▲ naik|▼ turun|■ datar>"`,
body `"Pos Pesanggrahan, <HH:MM> · <±rate> cm/jam · <next band> at <cm>"`
(EN equivalents), `tag: banjir-<band>`, `url: /?source=push`. All-clear:
`"Kembali normal · <cm> cm"`. Times in WIB.

### Monitoring (against silent death)

- `state.last_run_at / last_run_ok / last_error / failing_since` updated each
  run; `GET /api/push/status` returns them, the last reading's time and
  source, and the subscriber **count** only.
- Docker healthcheck fails if the last *completed* run (ok or not) is older
  than 15 min, so a hung loop shows as unhealthy in `docker ps`.
- **Owner alert:** if runs have failed for > 1 h, or the newest reading is
  older than 3 h, push once to subscriptions with `is_owner = 1` ("alerts
  can't read the river"), then again every 6 h while it lasts. The owner
  marks their phone by subscribing with a secret owner token (from
  `deploy/.env`) — e.g. a hidden `?owner=<token>` on the page.
  *(Claude's call; nothing about this is shown to residents.)*
- The page's "Alert service checked N min ago" line covers the case where the
  whole VPS is down (no server can push about its own death).

### Security

- Validate the subscription body: `endpoint` must be `https:` on a known push
  service host (`web.push.apple.com`, `fcm.googleapis.com`,
  `updates.push.services.mozilla.com`, `*.notify.windows.com`); keys are
  base64url of the expected lengths; body size capped (4 KB).
- Rate-limit `subscribe`/`unsubscribe`/`test` per client IP
  (`CF-Connecting-IP`), in memory; `test` at most once per minute per
  endpoint; subscriptions capped (e.g. 2 000) to bound storage and fan-out.
- CORS limited to the page origin; container runs as non-root, read-only
  root filesystem.

## Build order

1. `classify()` → `≥`, page tests updated.
2. Alert-rule engine + payload builder (pure, TDD).
3. Server: SQLite schema, watcher loop, Web Push sending, API, status,
   owner alert (TDD with faked upstream and a fake push sender).
4. VPS deployment: compose, tunnel + DNS setup, `deploy.sh`, VAPID keys.
5. Page: icons, SW push handler, subscribe/unsubscribe/test UI, status line,
   EN/ID copy.
6. End-to-end on the owner's iPhone: subscribe from the Home Screen app, test
   push, owner alert, then a forced-state push.

## Left to the builder

- HTTP framework (node:http, Hono, etc.) and SQLite driver (`better-sqlite3`
  or `node:sqlite`).
- `importScripts` vs `injectManifest` for the push handler.
- How the VAPID public key reaches the page (`/api/push/key` or a build-time
  env var).
- Whether the Cloudflare API token in `~/.config/mykid/cf_token` has the
  scopes for a second tunnel and DNS record, or a new token is needed (ask the
  owner before creating one).
- Exact EN/ID wording beyond the approved sketch.
